1서비스 개요

스트리머 인생게임은 SOOP 스트리머를 주인공 삼아, 유저가 0세부터 100세까지 그 인생을 3지선다로 대신 살아보는 인터랙티브 소설(생애 시뮬레이션) 웹게임입니다. 실제 스트리머 본인과는 무관한 가상의 인생이며, 매 선택이 재산·인기·행복·건강·관계 다섯 스탯을 흔들고 그 조합이 100세 시점의 엔딩을 정합니다.

  • 플랫폼: 단일 페이지 웹앱 (Vanilla JS + Firebase, 정적 호스팅 / GitHub Pages)
  • 대상: 스트리머 팬덤 커뮤니티, 익명 방문자 포함 누구나 즉시 참여 가능
  • 수익 모델: v1은 완전 무료 — 추후 보상형 광고("다시 태어나기" 등)·후원형 광고 추가 예정
  • 공유 인프라: StreamBet-Market·soop-stock-market·interior-3d-viewer와 동일한 Firebase 프로젝트(soop-stock-market)를 그대로 사용 — 스트리머 이름 검색에 필요한 stocks 노드를 새 프로젝트 없이 바로 읽기 위함

엔딩 화면은 "엔딩 문구 → 선택 요약 → 다른 유저 인생 → 재시작 안내" 순서로 고정돼 있다. 네 section 모두 showEnding() 한 곳에서 순서대로 hidden을 벗기며, 화면에 보이는 순서는 DOM 순서와 그대로 일치한다(버튼 두 개를 #endingSection에 몰아두던 이전 구조에서, "다시 태어나기"가 갤러리보다 먼저 보이던 걸 지금 순서로 바로잡음). choiceHistory는 submitChoice/rollDice가 마지막 구간을 완료할 때, 그리고 resumePlaythrough가 이미 완료된 판을 다시 불러올 때 둘 다 같은 buildChoiceHistory() 헬퍼로 계산돼 응답에 실린다 — DB에 별도로 저장하지 않고 choiceLog로부터 매번 다시 계산한다.

게임이 시작되면 상단 헤더(#mainHeader — eyebrow·제목·소개 문구)를 숨긴다. 대신 각 구간의 STAGES[].intro(1~2문장짜리 장면 설명, publicStage()가 그대로 전달)를 #gameSection 안 #storyText에 채워 "지금 어떤 이야기 안에 있는지"를 매 구간 새로 알려준다. 헤더는 게임 시작(startBtn)·이어하기(resumeBtn, 미완료 인생)·엔딩(showEnding) 세 지점에서 숨겨지고, 검색·이름짓기·이어하기 확인 화면에서는 그대로 보인다.

스탯 바는 스탯마다 다른 색으로 채워진다. 채움 너비는 항상 stats[key] 값 그대로(예: 50이면 50%), 색은 재산=골드·인기=코랄·행복=로즈·건강=세이지·관계=스카이로 고정 매핑 (STAT_COLORS). 선택지를 확정하면(직접 클릭이든 주사위든) 고르지 않은 나머지 선택지는 불투명도 30%로 흐려진다. 주사위 구간도 서버가 돌려준 choiceId로 어떤 미리보기가 뽑혔는지 표시하므로 동일하게 동작한다(markSelectedChoice()).

4생애 사이클 · 스탯 시스템

생애 10카테고리

균등한 나이 간격이 아니라 실제 인생의 결절점(입학·진로·독립·가정) 기준. 구현됨 10카테고리 — 생애 전체(0~100세)가 전부 구현 완료됐다. 형식은 동일해서 functions/game-data.js의 STAGES 배열에 이어 채우면 이후 콘텐츠도 확장 가능. 유아기·초등학생·청소년기·스무 살·사회 초년생·서른·중년·노년 준비·황혼은 카테고리가 STAGES 안에서 한 살 단위 여러 항목으로 쪼개져 있음 — 유아기는 7개(infancy-0~infancy-6), 초등학생은 6개(elementary-7~elementary-12), 청소년기는 6개(teen-13~ teen-18, 사춘기+고등학생을 한 카테고리로 통합 구현), 스무 살은 5개(twenties-19~ twenties-23), 사회 초년생은 6개(rookie-24~rookie-29), 서른은 10개(settling-30~settling-39), 중년은 15개(midlife-40~ midlife-54, 15년짜리로 가장 긴 카테고리라 항목도 제일 많음), 노년 준비는 15개 (oldprep-55~oldprep-69), 황혼은 31개 전부(twilight-70~ twilight-100, 70~100세). 표의 "구간" 개수와 실제 STAGES.length(현재 101)는 다르다.

구간나이상태
유아기 🎲 주사위(0~3세) + 선택(4~6세)0–6세구현됨
초등학생 선택 × 6(한 살 단위)7–12세구현됨
사춘기 청소년기로 통합 구현13–15세구현됨
고등학생 청소년기로 통합 구현16–18세구현됨
스무 살 선택 × 5(한 살 단위)19–23세구현됨
사회 초년생 선택 × 6(한 살 단위)24–29세구현됨
서른, 자리잡기 선택 × 10(한 살 단위)30–39세구현됨
중년, 선택의 무게 선택 × 15(한 살 단위)40–54세구현됨
노년 준비 선택 × 15(한 살 단위)55–69세구현됨
황혼 선택 × 31(70~100세, 한 살 단위)70–100세구현됨

실제 플레이 진행 속도: 0~4세는 선택 한 번에 1세씩, 5~99세부터는 선택 한 번에 1~5세씩 무작위로 건너뛴다. STAGES는 여전히 0~100세 101개 구간이 전부 채워져 있지만 (위 표는 콘텐츠가 얼마나 촘촘히 준비돼 있는지를 보여줄 뿐), 한 판을 실제로 플레이할 때 그 101개를 전부 다 방문하지는 않는다 — functions/index.js의 pickNextStageIndex()가 현재 나이(=stageIndex, STAGES 인덱스와 나이가 정확히 1:1)를 보고 다음에 몇 살로 넘어갈지 정한다: 5세 미만이면 항상 +1, 5세 이상 99세 이하면 1 + 남은-나이(100-현재나이)와 5 중 작은 값 이내에서 무작위로 널뛴다. 이 계산식 덕분에 무작위 폭이 100세를 절대 넘지 않고, 따라서 100세 구간은 스킵될 수 없이 반드시 그 판의 마지막 선택으로 방문된다(20,000회 시뮬레이션에서 경계 위반 0건, 100세 아닌 곳에서 완료된 사례 0건 확인). 건너뛴 나이는 애초에 STAGES의 그 인덱스가 서버로부터 한 번도 내려간 적이 없으므로, "지금까지 선택한 선택지" 로그 (choiceLog/choiceHistory, 7장·9장 참고)에도 자연히 나타나지 않는다 — 예를 들어 5세 다음이 9세로 건너뛰었다면 로그엔 5세 → 9세만 남고 6~8세 항목은 없다. 이 무작위 폭 조정으로 한 판의 평균 선택 횟수는 기존 101회에서 약 30~40회로 줄었다(시뮬레이션 평균 약 38회, 최소 29회~최대 50회).

100세 외에 "반드시 방문하는 나이"도 추가할 수 있다 — 지금은 54세(부모님과의 사별) 하나. MANDATORY_WAYPOINTS = [54] 배열에 나이를 넣어두면, pickNextStageIndex()가 무작위 폭을 정할 때 "100세까지 남은 거리" 대신 "아직 안 지난 가장 가까운 필수 방문 나이까지 남은 거리"를 기준으로 잘라낸다(그 나이를 지나고 나면 다음 필수 방문 나이 - 없으면 다시 100세 - 기준으로 돌아감). 100세 하나만 있을 때와 완전히 같은 증명으로, 이 나이도 스킵될 수 없이 반드시 방문된다(20,000회 시뮬레이션에서 54세 방문 20,000/20,000, 100세 정상 완주 20,000/20,000 — 둘 다 위반 0건). 다만 "나이를 방문하는 것"과 "그 나이의 특정 선택지가 뜨는 것"은 별개라, mandatory: true가 붙은 선택지는 pickVisibleChoiceIds()가 3개 무작위 추첨에서 절대 밀어내지 않고 항상 노출 목록에 포함시킨 뒤 나머지 자리만 무작위로 채운다 — 나이 방문 보장과 선택지 노출 보장을 합쳐야 진짜 "반드시 겪는 이벤트"가 된다. 물론 requiresFamilyMember 등 다른 게이팅 조건은 그대로 적용되므로, 54세에 부모님이 이미 안 계시면(더 이른 나이에 사별했거나 애초에 보육 시설 출신 등) 이 선택지 자체가 후보에서 빠지고 조용히 지나간다 — 시뮬레이션 기준 부모님이 남아있던 판의 100%에서 노출됐고, 결국 전체 판의 78.5%가 이 사별을 실제로 겪었다(21.5%는 54세 이전에 이미 부모님을 여의었거나 애초에 부모님이 없는 경우).

사별 사유는 고정 문구가 아니라 매번 무작위로 고른다. result 한 줄 대신 resultOptions(문구 배열)를 쓰면, applyChoice()가 반영 직후 그 중 하나를 무작위로 골라 응답에 담는다(무엇이 뽑혔는지는 따로 저장하지 않음 — 다른 선택 결과 문구와 마찬가지로 그 순간 한 번만 보여주는 연출). 지금 parent-passing-50s는 지병· 사고·노환·급성질환 4가지 사유를 담고 있고, 10,000회 추첨 시뮬레이션에서 24.2~25.7%로 고르게 분포함을 확인했다. 이 필드는 범용이라 다른 선택지에도 그대로 재사용 가능하다.

유아기(0~6세)는 한 살 단위로 7개 구간(infancy-0~infancy-6)으로 쪼개져 있지만, 주사위 굴리기는 그중 0~3세(infancy-0~infancy-3)까지만이다. 갓난아기~걸음마 시기에 벌어지는 일은 아이 본인이 "선택"할 수 있는 게 아니라는 취지로 이 네 구간만 random: true를 붙였다 — 클라이언트는 선택지를 클릭 불가능한 미리보기로만 보여주고 "🎲 주사위 굴리기" 버튼 하나만 누를 수 있으며, 서버(rollDice)가 직접 하나를 뽑아 반영한다. submitChoice는 random 구간을 아예 거부해서 클라이언트가 직접 골라 우회할 수 없다. 4~6세부터는 스스로 좋고 싫은 게 뚜렷해지는 나이라는 설정으로 다시 일반 3지선다(정확히는 6개 중 3개 노출)로 돌아간다.

초등학생(7~12세)도 유아기와 같은 방식으로 한 살 단위 6개 구간 (elementary-7~elementary-12)으로 쪼개져 있다. 다만 이 나이대는 전부 본인 의사로 고르는 게 자연스러워서 주사위 구간 없이 전부 일반 선택(6개 중 3개 노출)이다. 학교 적응(7세) → 교우관계 심화(8세) → 취미·특기 발견(9세) → 사춘기 전조(10세) → 진로·학업 스트레스 (11세) → 졸업·진학 준비(12세) 순으로 매년 다른 주제를 다룬다.

청소년기(13~18세)도 같은 방식으로 한 살 단위 6개 구간(teen-13~ teen-18)으로 쪼개져 있다. 기획안 원안의 "사춘기(13~15세)"·"고등학생(16~18세)" 두 카테고리를 하나의 name: '청소년기'로 통합해 구현했다(카테고리 표에는 여전히 두 줄로 따로 남아 있지만, 실제 콘텐츠는 이 6구간이 전부 대응). 신체·정서 변화(13세) → 교우관계 재편/자아 정체성(14세) → 진로 고민·고입 준비(15세) → 고등학교 입학(16세) → 진로 구체화·입시 스트레스(17세) → 수능·졸업(18세) 순. 역시 주사위 없이 전부 일반 선택.

스무 살(19~23세)도 같은 방식으로 한 살 단위 5개 구간(twenties-19~ twenties-23)으로 쪼개져 있다. 19세엔 대학·방송·취업 등 인생의 큰 방향을 가르는 원래 선택지 6개를 그대로 두고, 20~23세는 그 방향과 무관하게 벌어질 법한 일(자취·알바·인턴·취업 준비 등)로 새로 채웠다 — 자취 시작(20세) → 진로 구체화(21세) → 인턴·취업 현실(22세) → 첫 정규직· 자립(23세) 순. 이 게임은 이전 선택에 따라 이후 구간 내용이 달라지지 않으므로(스탯에만 반영), 19세에 뭘 골랐든 20~23세 선택지는 동일하게 노출된다.

사회 초년생(24~29세)도 같은 방식으로 한 살 단위 6개 구간(rookie-24~ rookie-29)으로 쪼개져 있다. 신입 적응(24세) → 업무 숙련·이직 고민(25세) → 독립· 재테크(26세) → 방향 재점검(27세) → 성과·책임 증가(28세) → 20대 정리(29세) 순.

서른, 자리잡기(30~39세)는 10년짜리 카테고리라 한 살 단위 10개 구간 (settling-30~settling-39)으로 구현했다 — 다른 카테고리(대부분 5~7년)보다 기간이 길어 항목 수도 그만큼 많다. 서른의 무게(30세) → 결혼·비혼(31세) → 내 집 마련·재테크(32세) → 가족계획(33세) → 커리어 전환점(34세) → 중간관리자(35세) → 부모 부양(36세) → 자기계발(37세) → 건강 체감(38세) → 서른대 마무리(39세) 순.

중년, 선택의 무게(40~54세)는 15년짜리로 가장 긴 카테고리라 한 살 단위 15개 구간 (midlife-40~midlife-54)으로 구현했다. 마흔의 무게(40세) → 자녀교육· 커리어 안정(41세) → 건강 이상 신호(42세) → 조직 내 입지(43세) → 관계 재정비(44세) → 중년의 위기 (45세) → 재도전(46세) → 부모님 노환·이별(47세) → 커리어 정점(48세) → 갱년기 초입(49세) → 쉰(50세) → 빈 둥지(51세) → 은퇴 준비(52세) → 재무 재점검(53세) → 중년 마무리(54세) 순.

노년 준비(55~69세)는 이제 15개 구간(oldprep-55~oldprep-69) 전부 구현됐다. 정년퇴직(55세) → 정체성 재정립(56세) → 새로운 관계망(57세) → 손주·가족 관계(58세) → 건강 관리 본격화(59세) → 환갑(60세) → 새 삶의 리듬(61세) → 연금(62세) → 취미·가족 심화(63세) → 몸의 변화 수용(64세) → 법정 노인 연령(65세) → 부부 관계 재조명(66세) → 유언·상속 정리(67세) → 상실 경험(68세) → 노년 준비 마무리(69세) 순.

황혼(70~100세, 31년)은 twilight-70~twilight-100 31개 전부 구현 완료됐다 — 이로써 생애 10카테고리(유아기~황혼) 전체가 채워졌다. 유아기~노년 준비까지는 이름이 STAGES 배열 안에서 카테고리별로 통일돼 있었는데, 황혼도 이 관례를 그대로 이어서 name: '황혼'으로 표기한다(구간 id 접두사만 twilight-). 칠순(70세) → 소소한 일상(71세) → 손주 세대 성취(72세) → 신체 저하 수용(73세) → 마지막 장거리 여행(74세) → 남은 삶 재구성(75세) → 배우자 간병(76세) → 희수(77세) → 기억력 저하 체감(78세) → 팔순 준비(79세) → 팔순(80세) → 감사한 하루하루(81세) → 오랜 인연들(82세) → 도움이 필요해짐(83세) → 삶의 의미 되새김(84세) → 요양·재가돌봄(85세) → 지혜를 전하는 어른(86세) → 잦아진 병원 방문(87세) → 미수(88세) → 구순 준비(89세) → 구순(90세) → 선물 같은 하루하루(91세) → 병상에서의 시간(92세) → 못다 한 말 전하기(93세) → 삶의 정리(94세) → 살아있음의 기적(95세) → 마음의 평화(96세) → 백수를 앞두고(97세) → 백 살을 실감(98세) → 백수(99세) → 백세, 인생의 완주(100세) 순.

구간마다 선택지를 최대 6개까지 써두고, 실제로는 그중 3개만 무작위로 노출한다. startPlaythrough/applyChoice가 그 구간에 들어설 때 pickVisibleChoiceIds()로 3개를 미리 뽑아 저장 슬롯(lifeGame/playthroughs/{uid}/visibleChoiceIds)에 남겨두고, publicStage()는 그 3개로 필터링해서만 클라이언트에 내려준다. 같은 판을 이어하기로 다시 열어도 저장해둔 3개가 그대로 다시 뜬다(재접속할 때마다 다른 선택지가 보이면 안 되므로). 주사위 구간의 rollDice도 반드시 이 3개 중에서만 뽑고, submitChoice도 노출되지 않은 선택지가 제출되면 거부한다 — "화면에 안 보여준 결과가 튀어나오는 일"을 서버가 막는다. 선택지가 3개 이하로만 채워진 구간(과거 콘텐츠)은 그냥 전부 보여준다.

상황 설명(intro)도 같은 원리로 여러 개 중 하나가 무작위로 뜨도록 메커니즘만 먼저 구현해뒀고, 상황별로 선택지까지 갈리는 것도 지원한다(2026-08-16, 콘텐츠는 아직 없음). 각 구간 상단의 상황 설명 한 줄(예: 0세 "세상에 막 태어난 순간...")은 지금까지 STAGES 항목마다 intro 단일 문자열 하나로 고정돼 있었는데, 사용자가 선택지처럼 "같은 나이라도 회차마다 다른 상황이 나올 수 있게" 해달라고 요청했다. 처음엔 상황 설명과 선택지를 완전히 독립적으로 무작위 추첨했는데, 그러면 "승진했다"는 상황에 "해고 통보에 좌절한다" 같은 선택지가 같이 뜰 수 있어 버그처럼 보일 위험이 있다는 지적을 받아, 선택지 쪽에도 requiresIntro로 상황과 연동할 수 있게 확장했다.

구조: STAGES 항목에 intros: [{id, text}, ...](배열)를 추가하면 pickIntroId(stage)가 그중 하나의 id를 무작위로 고른다(텍스트가 아니라 id를 저장 슬롯에 남기는 건 visibleChoiceIds가 선택지 텍스트가 아니라 id만 저장하는 것과 같은 이유 — 나중에 문구를 고쳐도 진행 중인 판이 옛 문구를 계속 들고 있지 않음). intros가 없는 구간은 pickIntroId가 null을 반환하고, resolveIntroText가 기존처럼 stage.intro 단일 문자열을 그대로 쓴다 — 즉 intros를 안 채운 구간은 동작이 전혀 안 바뀐다(지금 101개 전 구간이 여기 해당, 순수 시뮬레이션으로 회귀 없음 확인). 선택지에 requiresIntro: 'a'를 붙이면 pickVisibleChoiceIds()가 그 나이에 뽑힌 currentIntroId와 정확히 같을 때만 후보로 남긴다(기존 requiresCondition·requiresFamilyMember· requiresOccupation과 완전히 같은 게이팅 패턴 재사용) — requiresIntro가 없는 선택지는 어떤 상황이 뽑히든 항상 공용 후보로 남는다(상황별 전용 vs 공용 선택지를 자유롭게 섞을 수 있음). applyChoice()도 다른 requires* 체크와 나란히 choice.requiresIntro !== play.currentIntroId면 방어적으로 거부한다(위·변조 방지). 뽑힌 currentIntroId는 visibleChoiceIds와 똑같은 방식으로 저장 슬롯에 남겨 이어하기해도 같은 상황·같은 선택지 3개가 다시 뜬다 — startPlaythrough/ applyChoice의 다음 구간 전환/resumePlaythrough 세 곳 전부에 배선했고, publicStage(stage, visibleIds, introId)가 이 값을 받아 응답을 만든다. 나중에 특정 나이에 상황을 여러 개 쓰고 싶으면 그 STAGES 항목에 intros 배열과, 필요한 선택지에 requiresIntro만 추가하면 되고 로직 변경은 필요 없다(콘텐츠 작성 범위가 커서 — 101개 나이 전체에 적용하려면 나이당 2~3개씩 총 200~300개 상황 문구가 필요 — 이번엔 메커니즘까지만 구현하기로 함). 순수 Node 시뮬레이션으로 가상 2-상황(A/B) 구간을 만들어 2만 회 검증 - 상황 A 전용 선택지가 상황 B일 때 노출된 경우(cross contamination) 0건. 실제 배포된 함수에도 라이브로 재현해 시작(0세)·다음 구간 전환·새로고침 후 이어하기 세 경로 전부에서 정상 진행되는 것과 콘솔 에러 0건까지 확인했다.

재산 상세(현금·부동산·동산) — 선택지에 따라 현금성 자산·부동산·동산을 소유하게 된다. 건강/가족 상세와 완전히 같은 패턴이다: 일부 선택지에 addAsset({id,label,type})을 붙이면 그 재산이 그 판의 저장 슬롯(assets[])에 추가되고(이미 있으면 중복 추가 안 함), removeAsset(id)을 붙이면 처분돼서 빠진다(지금은 처분 선택지 없이 전부 취득만 있음). type은 cash(💰 현금성 자산 - 종잣돈·성과급·적금·퇴직금 등)· realestate(🏠 부동산 - 내 집·오피스텔·상가·별장 등)·movable(🚗 동산 - 차· 예물·가전·수집품 등) 세 가지다. 화면 상단 "현재 재산 상세" 패널(#assets)이 지금 소유한 재산을 계속 보여주고, 아무것도 없으면 "아직 소유한 재산 없음"으로 표시한다 — 건강/가족/직업 상세보다 위, 스탯 바 바로 아래에 배치했다(재산이 가장 먼저 눈에 띄어야 한다는 의도). 엔딩 화면에도 "남긴 재산"이라는 이름으로 동일하게 뜬다(가족·직업 이력과 나란히, 건강 상세는 애초에 엔딩 화면에 안 뜨는 것과 대비된다 — 재산은 가족처럼 "죽고 나서도 남는 것"이라는 판단).

전부 "발병 구간이 회복 구간보다 앞선다"는 순서만 지키면 되고, 발병 선택지와 회복 선택지는 각각 그 구간의 6~8개 선택지 풀 중 하나일 뿐이라 항상 뽑힌다는 보장은 없다(플레이마다 다른 조건을 겪거나 아예 하나도 안 겪을 수 있음) — 반복 플레이의 다양성을 위한 의도된 설계다. 새 조건을 추가할 땐 이 형식대로 발병용 선택지(addCondition)와 회복용 선택지 (requiresCondition + removeCondition)를 서로 다른(발병이 더 이른) 구간에 하나씩 짝지어 넣으면 된다 — 로직 변경은 필요 없다(단, rare-illness처럼 의도적으로 영구 지속시키고 싶다면 회복용 선택지를 아예 안 만들면 된다 — 코드는 모든 조건에 회복 짝이 있어야 한다고 강제하지 않는다).

건강 회복 디버프 — rare-illness·accident-aftereffects가 있으면 건강이 다시 오르지 않는다. addCondition에 blocksHealthRecovery: true를 얹으면(지금 이 둘) 그 조건을 갖고 있는 동안 모든 선택지의 deltas.health 중 양수만 0으로 깎인다(음수는 그대로 적용 — 더 나빠질 순 있어도 좋아지진 않는다). 예를 들어 천식 회복 선택지(asthma-managed, health +5)를 골라도 이 조건 중 하나라도 있으면 그 +5는 적용 안 된다. applyChoice()가 원본 choice.deltas를 effectiveDeltas로 복제해 이 규칙을 적용한 뒤 스탯에 반영하고, 응답의 deltas도 원본이 아니라 이 effectiveDeltas를 그대로 내려준다(클라이언트가 실제로 적용된 값과 다른 걸 보는 일이 없도록). 이번 선택에서 실제로 회복이 막혔을 때만 healthRecoverySuppressed: true를 같이 내려주고, 클라이언트는 이때만 결과 텍스트 아래에 그 원인을 덧붙인다 — 안 그러면 건강 바가 그대로인 게 버그처럼 보일 수 있어서. 이 문구는 healthConditions 중 blocksHealthRecovery가 실제로 true인 항목들의 label을 그대로 모아 만든다(예: "🩹 사고 후유증 때문에 건강이 회복되지는 않았다.", 둘 다 있으면 "🎗️ 희귀 난치병 · 🩹 사고 후유증 때문에...") — 예전엔 "🎗️ 난치병 때문에"로 문구가 고정돼 있어서 accident-aftereffects만 있는 플레이어에게도 "난치병 때문에"라고 잘못 표시되는 버그가 있었다(2026-08-16 사용자 스크린샷 제보로 발견, 라이브 재현으로 수정 확인). 조건 자체가 id별로 blocksHealthRecovery 플래그를 갖고 있어(하드코딩된 특정 id 체크가 아님) 나중에 다른 영구 조건을 추가해도 서버·클라이언트 모두 그대로 재사용 가능하다.

선택지 페이드아웃 — alzheimers가 있으면 선택지가 뜨자마자 10초에 걸쳐 서서히 투명해지다 완전히 사라진다. blocksHealthRecovery와 같은 패턴으로 addCondition에 causesChoiceFadeout: true를 얹으면(지금은 alzheimers가 유일) applyChoice()가 그 플래그를 그대로 healthConditions 항목에 실어 클라이언트로 내려보낸다 — 이 자체는 순수 클라이언트 연출이라 서버 쪽 스탯·확률 로직은 전혀 건드리지 않는다. 클라이언트는 매 구간 렌더링 (renderStage()) 때마다 지금 보유한 healthConditions 중 하나라도 causesChoiceFadeout이면 선택지 목록(#choiceList)에 opacity: 1 → 0을 10초(CHOICE_FADEOUT_MS) 동안 linear로 건다 — 화면 전환용 장식 트랜지션과 달리 실제 게임 난이도(제한 시간)라서 prefers-reduced-motion과 무관하게 항상 10초 고정이다. 트랜지션이 씹히지 않도록 먼저 transition: none과 opacity: 1을 강제 리플로우로 확정한 뒤에야 실제 트랜지션을 거는 방식은 구간 전환 페이드(fadeOut/fadeIn)와 동일한 기법이다. 조건이 없으면 인라인 스타일을 비워 정상 상태로 되돌린다.

가족 상세 — 선택지에 따라 태어날 때부터 100세까지 함께하는 가족이 정해지고, 생기고, 빠진다. 건강 상세와 완전히 같은 패턴을 쓰되, 한 조건이 여러 명을 한 번에 추가하거나 (예: 대가족으로 태어나면 아버지·어머니·형제자매 3명이 한 선택으로 동시에 생김), 부모님처럼 "그 중 아무거나 있으면 자격이 되고, 있는 걸 전부 제거"해야 하는 경우가 있어서 전부 배열로 받는다: addFamilyMembers([{id,label}, ...])는 나열된 가족을 그 판의 저장 슬롯 (familyMembers[])에 추가하고(이미 있는 id는 중복 추가 안 함), removeFamilyMembers ([id, ...])는 나열된 id 중 지금 있는 것만 제거한다. 노출 여부를 거르는 쪽은 requiresFamilyMember([id, ...])(그 중 하나라도 있어야 노출 후보)와 requiresNoFamilyMember([id, ...])(그 중 하나라도 있으면 후보에서 제외) — 예를 들어 "이혼한다"는 requiresFamilyMember:['spouse']라 배우자 없인 안 뜨고, "결혼한다"류는 requiresNoFamilyMember:['spouse']라 이미 결혼한 사람에겐 다시 안 뜬다. 화면 하단 "현재 가족 상세" 패널(#familyMembers)이 지금 가족 구성을 계속 보여주고, 엔딩 화면에도 "100세, 곁에 남은 가족" 패널(#endingFamilyMembers)로 최종 가족 구성을 따로 보여준다.

가족 상세 게이팅 감사(2026-08-16) — 없는 가족을 언급하는 선택지가 뜨던 문제를 전수 조사해 고쳤다. 가족·직업 기능을 처음 붙일 때는 결혼·출산·부모님 사망 등 그 관계를 "만들거나 없애는" 선택지만 requiresFamilyMember로 게이팅했고, 이미 있는 관계를 전제로 한(형제자매·배우자·자녀·손주가 텍스트에 등장하지만 add/remove는 안 하는) 주변 선택지들은 의도적으로 손대지 않았었다 — 그 결과 자녀를 가진 적 없는 플레이어에게 "빈 둥지 증후군을 겪는다" 같은 선택지가 뜨는 등, 없는 가족을 전제로 한 선택지가 섞여 나오는 문제가 있었다. 전체 STAGES를 형제자매/배우자/자녀/손주 키워드로 훑어 game-data.js의 모든 선택지를 대조한 결과 41개 선택지에 게이팅이 빠져있었던 걸 확인하고 전부 requiresFamilyMember를 추가했다(형제자매 2개, 배우자 6개, 자녀 19개, 손주 14개). 부모님 부양(중년 47세 caring-for-parent-with-siblings) 처럼 "부모님도 계시고 형제자매도 있어야" 하는 것처럼 서로 다른 두 조건이 동시에(AND로) 필요한 경우를 위해 requiresAllFamilyMemberGroups: [[id,...], [id,...]](하위 배열끼리는 AND, 각 하위 배열 안에서는 OR)도 새로 추가했다. 이 감사 과정에서 황혼 72세 (twilight-72)는 6개 선택지 중 5개가 손주/자녀 게이팅 대상이라 게이팅 후 자녀·손주가 없는 플레이어에게 1개만 남는 문제가 발견돼, 가족과 무관한 선택지 2개(취미 목표 세우기, 동네 친구 모임)를 추가로 새로 써넣었다. 검증은 20,000회 시뮬레이션으로 (1) 게이팅 위반 0건 (2) 어떤 나이·어떤 가족 구성에서도 노출 가능한 선택지가 0개가 되는 경우 0건임을 확인했다.

직업 상세 — 건강·가족과 달리 저장 슬롯에 별도 필드가 없다. 직업은 동시에 여러 개 쌓이는 목록이 아니라 항상 "지금 하나"라, 선택지에 setOccupation({id,label})을 붙이면 그 직업으로 그냥 덮어쓴다(추가·제거 개념 없음). 그리고 이 값은 저장 슬롯에 따로 기록해두지 않고 choiceLog에서 매번 다시 계산한다 — setOccupation이 붙은 선택만 골라 시간순으로 나열하면 그게 곧 직업 이력이고, 그 마지막 항목이 현재 직업이다(7장 "지금까지 선택한 선택지"의 choiceHistory와 완전히 같은 계산 방식, buildOccupationHistory()). 별도 필드가 없으니 동기화가 어긋날 일도 없다. 노출 필터링은 requiresOccupation([id,...]) — 지금 직업이 그 중 하나여야 노출 후보가 된다(예: "재취업한다"는 requiresOccupation:['retired']라 은퇴한 적 없으면 안 뜬다). 게임 진행 중엔 현재 직업 하나만 진행 화면의 "현재 직업 상세" 패널(#currentOccupation)에 배지 하나로 보여주고, 없으면 "아직 특별한 직업 없음"으로 표시한다. 엔딩 화면에서만 전체 이력을 "지금까지의 직업 이력" 패널(#occupationHistoryList, 선택 요약과 같은 행 스타일 재사용)로 보여준다 — 진행 중엔 지금 상태만, 다 살고 나서야 그 흐름 전체를 돌아보게 하는 의도적 구분.

5선택지 작성 원칙

선택지 문장만 보고 결과를 예측할 수 없어야 한다. deltas·result는 서버(functions/index.js의 publicStage())가 선택 전엔 절대 클라이언트로 보내지 않는다 — 개발자 도구로 응답을 뜯어봐도 안 보임.

지양 — 결과가 문장에 이미 있음

  • "안정적인 대기업에 입사한다 (+재산, −인기)"
  • "위험을 감수하고 창업한다 (재산 ±큰 변동)"

지향 — 태도만 드러냄

  • "다니던 학교를 관두고 방송을 시작해본다"
  • "바로 돈이 되는 기술을 배워 취업 전선에 뛰어든다"

한 구간에 선택지를 최대 6개까지 써두고, 실제 플레이에선 그중 3개만 무작위로 노출한다(구현 방식은 4장 참고) — 그래서 6개를 안전/도전/우회 세 태도로 두 개씩 짝지어 써두면, 어떤 3개가 뽑히든 자연스럽게 톤이 섞인다. 매번 다른 톤을 새로 짜내는 대신, 이 뼈대 위에서 구간별 소재만 갈아 끼운다.

9시스템 흐름도

이어하기 확인 흐름 (계정당 저장 슬롯 1개)

로그인 확정(익명 포함)
→
클라이언트가 lifeGame/playthroughs/{uid}를 직접 읽음(함수 호출 없음)
→
completed:false면 "이어하기" 화면, 아니면 검색 화면
→
"이어하기" 클릭 시에만 resumePlaythrough 호출 → 지금 구간 반환

매 선택마다 서버가 이미 저장 슬롯에 진행 상태를 쓰고 있어서 별도의 "저장" 동작은 없다 — 여기서 하는 건 "저장 여부 확인 + 이어서 보여주기"뿐이다. "새로 시작하기"를 고르면 startPlaythrough가 기존 저장을 그대로 덮어쓴다(계정당 슬롯이 1개라 여러 판을 동시에 보관하지 않음). 선택 결과가 뜰 때마다 화면 하단에 "💾 자동저장 되었습니다" 토스트(#toast, showToast())가 잠깐 떴다 사라지는데, 이건 낙관적 표시가 아니라 applyChoice가 playRef.update()를 이미 끝내고 응답한 뒤에만 호출되므로 실제 저장 완료를 그대로 반영한다.

인생 시작 흐름

스트리머 검색
→
이름 확정
→
startPlaythrough 호출
→
서버: 플레이스루 생성 + 스탯 초기화(50/50/50/50/50)
→
첫 구간 렌더

선택 제출 흐름

선택지 클릭
→
submitChoice 호출(choiceId만 전송)
→
서버: game-data.js에서 deltas 조회
→
서버: 스탯 반영(clamp 0~100) + 통계 카운터 증가
→
서버: pickNextStageIndex()로 다음 나이 결정(0~4세는 +1, 5~99세는 100을 넘지 않는 선에서 +1~+5 무작위)
→
100세에서 낸 선택이면 엔딩 판정, 아니면 그 나이의 다음 구간 반환

주사위 굴리기 흐름 (유아기 전용)

🎲 주사위 굴리기 클릭 (인자 없음, uid는 인증 토큰으로 식별)
→
서버: visibleChoiceIds로 한정한 뒤 그중 하나를 균등 확률로 직접 뽑음
→
이후는 submitChoice와 동일하게 반영
→
응답에 어떤 환경이 뽑혔는지(choiceText)도 포함

엔딩 화면 노출 순서

100세 구간 완료(또는 완료된 판을 resumePlaythrough로 재열람)
→
① 엔딩 문구 + 최종 스탯(#endingSection)
→
② 지금까지 선택한 선택지 전체(#choiceHistorySection, choiceLog→STAGES 대조)
→
③ 다른 유저 인생 갤러리(#gallerySection) + 공유하기 버튼
→
④ 재시작 안내(#restartSection, "다시 태어나기")

→
다른 유저 화면에 실시간 반영
