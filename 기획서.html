1서비스 개요

스트리머 인생게임은 SOOP 스트리머를 주인공 삼아, 유저가 0세부터 100세까지 그 인생을 3지선다로 대신 살아보는 인터랙티브 소설(생애 시뮬레이션) 웹게임입니다. 실제 스트리머 본인과는 무관한 가상의 인생이며, 매 선택이 재산·인기·행복·건강·관계 다섯 스탯을 흔들고 그 조합이 100세 시점의 엔딩을 정합니다.

  • 플랫폼: 단일 페이지 웹앱 (Vanilla JS + Firebase, 정적 호스팅 / GitHub Pages)
  • 대상: 스트리머 팬덤 커뮤니티, 익명 방문자 포함 누구나 즉시 참여 가능
  • 수익 모델: v1은 완전 무료 — 추후 보상형 광고("다시 태어나기" 등)·후원형 광고 추가 예정
  • 공유 인프라: StreamBet-Market·soop-stock-market·interior-3d-viewer와 동일한 Firebase 프로젝트(soop-stock-market)를 그대로 사용 — 스트리머 이름 검색에 필요한 stocks 노드를 새 프로젝트 없이 바로 읽기 위함

4생애 사이클 · 스탯 시스템

생애 10카테고리

균등한 나이 간격이 아니라 실제 인생의 결절점(입학·진로·독립·가정) 기준. 구현됨 9카테고리, 부분 구현 1카테고리 — 형식은 동일해서 functions/game-data.js의 STAGES 배열에 이어 채우면 됨. 유아기·초등학생·청소년기·스무 살·사회 초년생·서른·중년·노년 준비·황혼은 카테고리가 STAGES 안에서 한 살 단위 여러 항목으로 쪼개져 있음 — 유아기는 7개(infancy-0~infancy-6), 초등학생은 6개(elementary-7~elementary-12), 청소년기는 6개(teen-13~ teen-18, 사춘기+고등학생을 한 카테고리로 통합 구현), 스무 살은 5개(twenties-19~ twenties-23), 사회 초년생은 6개(rookie-24~rookie-29), 서른은 10개(settling-30~settling-39), 중년은 15개(midlife-40~ midlife-54, 15년짜리로 가장 긴 카테고리라 항목도 제일 많음), 노년 준비는 15개 전부 구현(oldprep-55~oldprep-69), 황혼은 70~90세 21개까지 구현 (twilight-70~twilight-90) — 91~100세는 아직 TODO. 표의 "구간" 개수와 실제 STAGES.length(현재 91)는 다르다.

유아기(0~6세)는 한 살 단위로 7개 구간(infancy-0~infancy-6)으로 쪼개져 있지만, 주사위 굴리기는 그중 0~3세(infancy-0~infancy-3)까지만이다. 갓난아기~걸음마 시기에 벌어지는 일은 아이 본인이 "선택"할 수 있는 게 아니라는 취지로 이 네 구간만 random: true를 붙였다 — 클라이언트는 선택지를 클릭 불가능한 미리보기로만 보여주고 "🎲 주사위 굴리기" 버튼 하나만 누를 수 있으며, 서버(rollDice)가 직접 하나를 뽑아 반영한다. submitChoice는 random 구간을 아예 거부해서 클라이언트가 직접 골라 우회할 수 없다. 4~6세부터는 스스로 좋고 싫은 게 뚜렷해지는 나이라는 설정으로 다시 일반 3지선다(정확히는 6개 중 3개 노출)로 돌아간다.

초등학생(7~12세)도 유아기와 같은 방식으로 한 살 단위 6개 구간 (elementary-7~elementary-12)으로 쪼개져 있다. 다만 이 나이대는 전부 본인 의사로 고르는 게 자연스러워서 주사위 구간 없이 전부 일반 선택(6개 중 3개 노출)이다. 학교 적응(7세) → 교우관계 심화(8세) → 취미·특기 발견(9세) → 사춘기 전조(10세) → 진로·학업 스트레스 (11세) → 졸업·진학 준비(12세) 순으로 매년 다른 주제를 다룬다.

청소년기(13~18세)도 같은 방식으로 한 살 단위 6개 구간(teen-13~ teen-18)으로 쪼개져 있다. 기획안 원안의 "사춘기(13~15세)"·"고등학생(16~18세)" 두 카테고리를 하나의 name: '청소년기'로 통합해 구현했다(카테고리 표에는 여전히 두 줄로 따로 남아 있지만, 실제 콘텐츠는 이 6구간이 전부 대응). 신체·정서 변화(13세) → 교우관계 재편/자아 정체성(14세) → 진로 고민·고입 준비(15세) → 고등학교 입학(16세) → 진로 구체화·입시 스트레스(17세) → 수능·졸업(18세) 순. 역시 주사위 없이 전부 일반 선택.

스무 살(19~23세)도 같은 방식으로 한 살 단위 5개 구간(twenties-19~ twenties-23)으로 쪼개져 있다. 19세엔 대학·방송·취업 등 인생의 큰 방향을 가르는 원래 선택지 6개를 그대로 두고, 20~23세는 그 방향과 무관하게 벌어질 법한 일(자취·알바·인턴·취업 준비 등)로 새로 채웠다 — 자취 시작(20세) → 진로 구체화(21세) → 인턴·취업 현실(22세) → 첫 정규직· 자립(23세) 순. 이 게임은 이전 선택에 따라 이후 구간 내용이 달라지지 않으므로(스탯에만 반영), 19세에 뭘 골랐든 20~23세 선택지는 동일하게 노출된다.

사회 초년생(24~29세)도 같은 방식으로 한 살 단위 6개 구간(rookie-24~ rookie-29)으로 쪼개져 있다. 신입 적응(24세) → 업무 숙련·이직 고민(25세) → 독립· 재테크(26세) → 방향 재점검(27세) → 성과·책임 증가(28세) → 20대 정리(29세) 순.

서른, 자리잡기(30~39세)는 10년짜리 카테고리라 한 살 단위 10개 구간 (settling-30~settling-39)으로 구현했다 — 다른 카테고리(대부분 5~7년)보다 기간이 길어 항목 수도 그만큼 많다. 서른의 무게(30세) → 결혼·비혼(31세) → 내 집 마련·재테크(32세) → 가족계획(33세) → 커리어 전환점(34세) → 중간관리자(35세) → 부모 부양(36세) → 자기계발(37세) → 건강 체감(38세) → 서른대 마무리(39세) 순.

중년, 선택의 무게(40~54세)는 15년짜리로 가장 긴 카테고리라 한 살 단위 15개 구간 (midlife-40~midlife-54)으로 구현했다. 마흔의 무게(40세) → 자녀교육· 커리어 안정(41세) → 건강 이상 신호(42세) → 조직 내 입지(43세) → 관계 재정비(44세) → 중년의 위기 (45세) → 재도전(46세) → 부모님 노환·이별(47세) → 커리어 정점(48세) → 갱년기 초입(49세) → 쉰(50세) → 빈 둥지(51세) → 은퇴 준비(52세) → 재무 재점검(53세) → 중년 마무리(54세) 순.

노년 준비(55~69세)는 이제 15개 구간(oldprep-55~oldprep-69) 전부 구현됐다. 정년퇴직(55세) → 정체성 재정립(56세) → 새로운 관계망(57세) → 손주·가족 관계(58세) → 건강 관리 본격화(59세) → 환갑(60세) → 새 삶의 리듬(61세) → 연금(62세) → 취미·가족 심화(63세) → 몸의 변화 수용(64세) → 법정 노인 연령(65세) → 부부 관계 재조명(66세) → 유언·상속 정리(67세) → 상실 경험(68세) → 노년 준비 마무리(69세) 순.

황혼(70~100세, 31년)은 twilight-70~twilight-90(70~90세, 21개)까지 구현됐다. 91~100세는 아직 TODO. 유아기~노년 준비까지는 이름이 STAGES 배열 안에서 카테고리별로 통일돼 있었는데, 황혼도 이 관례를 그대로 이어서 name: '황혼'으로 표기한다(구간 id 접두사만 twilight-). 칠순(70세) → 소소한 일상(71세) → 손주 세대 성취(72세) → 신체 저하 수용(73세) → 마지막 장거리 여행(74세) → 남은 삶 재구성(75세) → 배우자 간병(76세) → 희수(77세) → 기억력 저하 체감(78세) → 팔순 준비(79세) → 팔순(80세) → 감사한 하루하루(81세) → 오랜 인연들(82세) → 도움이 필요해짐(83세) → 삶의 의미 되새김(84세) → 요양· 재가돌봄(85세) → 지혜를 전하는 어른(86세) → 잦아진 병원 방문(87세) → 미수(88세) → 구순 준비 (89세) → 구순(90세) 순.

구간마다 선택지를 최대 6개까지 써두고, 실제로는 그중 3개만 무작위로 노출한다. startPlaythrough/applyChoice가 그 구간에 들어설 때 pickVisibleChoiceIds()로 3개를 미리 뽑아 저장 슬롯(lifeGame/playthroughs/{uid}/visibleChoiceIds)에 남겨두고, publicStage()는 그 3개로 필터링해서만 클라이언트에 내려준다. 같은 판을 이어하기로 다시 열어도 저장해둔 3개가 그대로 다시 뜬다(재접속할 때마다 다른 선택지가 보이면 안 되므로). 주사위 구간의 rollDice도 반드시 이 3개 중에서만 뽑고, submitChoice도 노출되지 않은 선택지가 제출되면 거부한다 — "화면에 안 보여준 결과가 튀어나오는 일"을 서버가 막는다. 선택지가 3개 이하로만 채워진 구간(과거 콘텐츠)은 그냥 전부 보여준다.

건강 상세(부상·질병) — 선택지가 건강을 "생기게" 하거나 "낫게" 한다. 일부 선택지에 addCondition({id,label})을 붙이면 해당 부상/질병이 그 판의 저장 슬롯 (healthConditions[])에 추가되고, removeCondition(id)을 붙이면 해당 조건이 빠진다(예: 2세 "정글짐에서 뛰어내리다 팔이 부러진다" → 4세 "깁스를 풀고 팔을 마음껏 쓸 수 있게 된다"). 회복용 선택지엔 requiresCondition(id)도 함께 붙는데, 그 조건이 지금 없으면 pickVisibleChoiceIds()가 애초에 노출 후보에서 제외한다 — 부러진 적 없는 팔이 "다 나았다"고 나오는 일이 없도록. 이 회복용 선택지는 반드시 3개 노출에 들어갈 필요는 없고, 그 조건을 가진 플레이어에게만 가끔 등장하면 충분하다. 화면 하단 "현재 건강 상세" 패널(#healthConditions)이 지금 앓고 있는 조건을 계속 보여주고, 아무것도 없으면 "특별한 건강 이슈 없음"으로 표시한다.

전부 "발병 구간이 회복 구간보다 앞선다"는 순서만 지키면 되고, 발병 선택지와 회복 선택지는 각각 그 구간의 6~8개 선택지 풀 중 하나일 뿐이라 항상 뽑힌다는 보장은 없다(플레이마다 다른 조건을 겪거나 아예 하나도 안 겪을 수 있음) — 반복 플레이의 다양성을 위한 의도된 설계다. 새 조건을 추가할 땐 이 형식대로 발병용 선택지(addCondition)와 회복용 선택지 (requiresCondition + removeCondition)를 서로 다른(발병이 더 이른) 구간에 하나씩 짝지어 넣으면 된다 — 로직 변경은 필요 없다.

5선택지 작성 원칙

선택지 문장만 보고 결과를 예측할 수 없어야 한다. deltas·result는 서버(functions/index.js의 publicStage())가 선택 전엔 절대 클라이언트로 보내지 않는다 — 개발자 도구로 응답을 뜯어봐도 안 보임.

지양 — 결과가 문장에 이미 있음

  • "안정적인 대기업에 입사한다 (+재산, −인기)"
  • "위험을 감수하고 창업한다 (재산 ±큰 변동)"

지향 — 태도만 드러냄

  • "다니던 학교를 관두고 방송을 시작해본다"
  • "바로 돈이 되는 기술을 배워 취업 전선에 뛰어든다"

한 구간에 선택지를 최대 6개까지 써두고, 실제 플레이에선 그중 3개만 무작위로 노출한다(구현 방식은 4장 참고) — 그래서 6개를 안전/도전/우회 세 태도로 두 개씩 짝지어 써두면, 어떤 3개가 뽑히든 자연스럽게 톤이 섞인다. 매번 다른 톤을 새로 짜내는 대신, 이 뼈대 위에서 구간별 소재만 갈아 끼운다.
